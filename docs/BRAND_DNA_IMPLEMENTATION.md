# Brand DNA — Implementation Instructions

## 1. Purpose

This document defines how the existing AI Social Media application must implement the Brand DNA product described in:

`docs/BRAND_DNA_PRODUCT_SPEC.md`

The product specification is the source of truth for the product vision, principles, UX direction, stages, and long-term behavior.

This document is the source of truth for how engineering work should be approached.

When these instructions conflict with speculative implementation ideas, stop and inspect the product specification and existing application before proceeding.

---

# 2. Core Product Principle

The goal is NOT to make the application generate more social posts.

The goal is to make the application understand the person or brand well enough to create content that:

> Sounds like them, but is better expressed.

The user's knowledge, experience, language, opinions, stories, preferences, and corrections are the valuable source material.

AI performs the writing, structuring, improvement, and eventually channel-placement work.

The user remains the expert.

The system must never manufacture expertise to compensate for missing user information.

---

# 3. Product Thesis

The Brand DNA system should evolve from:

    Brand profile
        ↓
    Generic AI generation

into:

    Brand
        ↓
    Brand Promise
        ↓
    Lived Expertise
        ↓
    Natural Voice
        ↓
    User Taste
        ↓
    Channel Context
        ↓
    Better Content
        ↓
    User Feedback
        ↓
    Improved Brand DNA

The long-term objective is compounding personalization.

A new user should not receive a fake personality generated by AI.

The system should progressively learn the user's real communication patterns from evidence.

---

# 4. Source of Truth Hierarchy

When deciding what the system should believe about a brand, use this conceptual hierarchy:

1. Explicit user rules
2. Explicit user-provided information
3. User-approved content or corrections
4. Repeated observed behavior
5. Single observed behavior
6. AI inference

Higher-authority information must not be silently overridden by lower-authority inference.

Example:

If the user explicitly says:

    "Never use the word hustle."

The system must treat that differently from:

    "The user has not used the word hustle in five posts."

The first is an explicit preference.

The second is an observation.

Do not turn weak observations into permanent brand rules without sufficient evidence.

---

# 5. Evidence Over Assumption

Every future Brand DNA capability should be designed around evidence.

The system should be able to conceptually distinguish:

- User-provided information
- User-provided examples
- Interview answers
- Approved content
- User edits
- User refusals
- Observed patterns
- AI-inferred patterns

Do not present an AI inference as if the user explicitly told us something.

Do not invent confidence.

Do not invent evidence.

Do not claim the system "knows" a preference unless there is evidence supporting it.

---

# 6. Staged Implementation

Brand DNA must be implemented progressively.

The stages are:

## Stage 1 — Brand Promise

Capture:

- Who they help
- What they actually do or sell
- Who they are not for
- Topics they will not touch
- What a good week of content should change

---

## Stage 2 — Your Words

Capture the user's lived expertise through:

- Audio interview
- Transcript
- Existing captions
- Typed answers

The preferred future experience is an audio-first interview.

Typing and paste remain valid alternatives.

---

## Stage 3 — Voice Study

Study the user's actual corpus.

Identify:

### KEEP

How the user naturally communicates:

- sentence openings
- vocabulary
- rhythm
- first-person usage
- slang
- humor
- emoji behavior
- typical length
- recurring expressions

### RAISE

Where the user's communication can be improved:

- weak opening
- buried point
- rambling
- unnecessary jargon
- weak CTA
- unclear structure
- marketing language that does not sound natural

Do not build Stage 3 until Stage 1–2 provide sufficient real user material.

---

## Stage 4 — One Idea, One Room

The system eventually uses:

    One insight
        +
    One channel
        =
    One appropriately shaped post

Do not automatically clone the same caption across every channel.

The expertise remains the same.

The expression changes according to the channel.

---

## Stage 5 — Edit and Learn

User edits become learning signals.

Conceptually:

    AI output
        ↓
    User edit
        ↓
    Before / After
        ↓
    Meaningful preference
        ↓
    Future generation improvement

Do not treat trivial spelling or punctuation corrections as major personality signals.

Meaningful changes are valuable.

Examples:

- "I would never say this."
- "Too salesy."
- "Remove this opener."
- "This sounds corporate."
- "I would say it much more directly."

These can become future evidence.

---

## Stage 6 — Proof

Eventually measure whether the system is becoming more useful through signals such as:

- fewer edits
- more accepted drafts
- reuse of expertise
- stronger user recognition
- repeated use of the user's actual ideas
- audience language

Do not reduce Brand DNA quality to an arbitrary AI score.

---

# 7. CURRENT IMPLEMENTATION SCOPE

## IMPORTANT

The current implementation scope is:

# Stage 1 + Stage 2 only

Do NOT implement Stage 3–6 unless explicitly requested.

The current objective is to make a brand capable of containing:

    Brand Promise
        +
    User's Words

# 8. Stage 1 — Brand Promise

The existing brand model already contains some useful information.

Do not create a separate competing "strategy product" if the existing brand profile can be extended appropriately.

The conceptual Brand Promise should capture:

- Business name
- Who they help
- What they actually do
- Who they are not for
- Topics they will not touch
- Desired outcome from content

Existing useful fields should be reused where appropriate.

Examples:

- `target_audience`
- `services`
- `forbidden_topics`

Potential additional concepts:

- `not_for`
- `desired_outcome`

Do not add fields merely because they appear in this document.

First inspect the existing backend model and API.

---

# 9. Stage 1 UX

The Brand experience should feel like:

> "Tell us who you are."

It should NOT feel like:

> "Complete your AI marketing configuration."

Prefer simple language.

Avoid unnecessary marketing terminology.

Avoid exposing:

- LLM
- Ollama
- prompt engineering
- agents
- model names
- embeddings
- vector databases
- AI training terminology

The user should not feel like they are configuring an AI system.

They should feel like they are helping an editor understand them.

---

# 10. Brand Home

The long-term Brand Home concept has three areas:

1. Promise
2. Your Words
3. Draft

For the current implementation:

- Promise is active.
- Your Words is active.
- Draft may be visible but locked.
- Draft must NOT perform the future Stage 4 generation behavior yet.

The UI should communicate progression without fake percentages.

Prefer:

    Promise → Words → Draft

over:

    "Brand is 63% trained"

Never create a fake training score.

---

# 11. Stage 2 — Your Words

The purpose of Stage 2 is to capture the user's actual knowledge.

The system should collect source material such as:

- Interview answers
- Existing captions
- Typed answers

The original user wording is valuable.

Do not automatically rewrite the user's answers into polished marketing language.

Store the source material as the user's material.

The distinction between:

    what the user said

and:

    what AI inferred from what they said

must remain clear.

---

# 12. Audio Interview

The product specification defines an audio-first interview as the preferred future capture mechanism.

The intended experience is approximately:

- 8–10 minutes
- prepared questions
- short cold open
- preparation pause
- focused questions
- at most one useful follow-up
- closing question
- transcript review

The interviewer should be:

- quiet
- curious
- short
- specific
- non-performative

Avoid:

- avatars
- excessive encouragement
- fake enthusiasm
- long explanations
- generic coaching language
- repeated follow-up questions

The user should always be able to:

- mute the interviewer
- read the question
- answer by typing
- paste existing content

Audio must never become the only path.

---

# 13. Important Audio Constraint

Do not introduce a hosted interview copilot merely because it is technically easier.

The product specification intentionally favors the existing local AI direction.

When this capability is eventually implemented, inspect the existing local Ollama/STT architecture first.

Potential future components include:

- local Whisper-class STT
- existing local Ollama stack for preparation and sorting
- optional local TTS

However:

DO NOT implement the complete audio stack during Stage 1 unless the current approved implementation scope explicitly includes it.

Do not build infrastructure merely because the future architecture mentions it.

---

# 14. Interview Preparation

The future interviewer must be prepared from information the user has already supplied.

Preparation may use:

- Brand Promise
- previous interview answers
- pasted samples
- existing user-provided material

Preparation must NOT invent facts about the business.

Never ask a question based on a fabricated assumption.

For example, do not generate:

> "Your customers have told you..."

unless the user actually supplied evidence that customers said this.

---

# 15. Existing Content as Evidence

If the user supplies existing posts/captions, treat them as source material.

Do not immediately transform them into a generic "brand voice."

First preserve the original material.

Later stages may analyze the corpus.

The system should eventually be able to distinguish:

    SOURCE MATERIAL
    ↓
    ANALYSIS
    ↓
    OBSERVED PATTERN
    ↓
    INFERENCE

Do not collapse these into one opaque AI-generated profile.

---

# 16. Generation Guardrails

Brand DNA must eventually influence generation.

When that happens, generation should be grounded in this order:

1. User's actual source material
2. Voice guidance derived from that material
3. Channel-specific requirements
4. Brand Promise

The generator must NOT:

- invent business facts
- invent products
- invent services
- invent customer stories
- invent personal experiences
- invent opinions
- invent a personality
- fabricate expertise
- replace the user's worldview with generic AI language

If there is insufficient information, the system should ask for more source material rather than manufacture it.

---

# 17. "Like Me, But Better"

This is a central product behavior.

Better does NOT mean:

- more corporate
- more polished for its own sake
- more hashtags
- more buzzwords
- longer captions
- more emojis
- more marketing language

Better means improving things such as:

- opening
- clarity
- focus
- structure
- usefulness
- CTA
- channel fit

while preserving:

- user's knowledge
- user's point of view
- user's natural language
- user's personality
- user's recognizable communication style

Do not optimize away the user's identity.

---

# 18. Channel Behavior

Channels are placement environments.

They are not simply destinations to duplicate content into.

Eventually:

    Same insight
        ↓
    Different channel
        ↓
    Different useful expression

For example, conceptually:

LinkedIn:
- argument
- proof
- professional point of view

Instagram:
- felt moment
- concise expression
- visual context

Facebook:
- conversation
- community interaction

These are conceptual guidelines only.

Before implementing channel-specific behavior, inspect the existing product and actual supported backend capabilities.

Do not invent unsupported publishing behavior.

---

# 19. User × Brand × Channel

Eventually preferences may exist at the intersection of:

    User
      ×
    Brand
      ×
    Channel

Do not implement a complex preference engine prematurely.

Start with the smallest representation that supports the current UX.

Do not create a generic rules engine or configuration platform.

---

# 20. Edit Learning

Edit learning is intentionally future scope.

Do not implement a sophisticated learning system during Stage 1–2.

However, the Stage 1–2 architecture should avoid making future learning impossible.

When editing is eventually implemented:

- retain original generated content
- retain user's edited content
- distinguish meaningful edits from trivial edits
- use meaningful differences as evidence
- avoid silently changing permanent Brand DNA from a single edit

Repeated evidence should carry more weight than one-off changes.

---

# 21. Do Not Build a Generic AI Persona

The system must NOT create:

> "Your AI persona"

based on a handful of generic preferences.

Avoid shallow profiles such as:

- professional
- friendly
- funny
- inspirational
- bold

These may be useful as minor descriptors, but they are not the Brand DNA.

Real Brand DNA should eventually come from actual evidence.

- existing content generation

- social accounts

# 25. Backend Is the Contract

The backend API remains the source of truth.

Before implementing any frontend Brand DNA feature:

1. Inspect the actual backend model.
2. Inspect the actual route.
3. Inspect request and response schemas.
4. Inspect repository/service behavior.
5. Inspect existing frontend API client patterns.
6. Determine whether the existing contract supports the required UX.

Never invent an endpoint because it would be convenient.

Never assume a field exists.

Never create a frontend fake API to hide a missing backend capability.

---

# 26. Backend Read-Only Rule

During frontend Brand DNA implementation:

The backend is READ-ONLY unless the user explicitly approves backend changes.

If the frontend requires backend support that does not exist:

STOP that dependent slice.

Report:

    BACKEND CHANGE SUGGESTION

Include:

- missing capability
- current backend behavior
- why the frontend requires it
- smallest proposed backend change
- whether the change is breaking or non-breaking

Do not silently modify the backend.

---

# 27. Existing Architecture

Follow the existing frontend architecture.

Expected direction:

    UI
      ↓
    Feature hook
      ↓
    Typed API service
      ↓
    Shared API client
      ↓
    Next.js rewrite
      ↓
    FastAPI backend

Do not scatter raw `fetch()` calls throughout components.

Do not create feature-specific API abstractions that bypass the shared client unless there is a documented reason.

Use strict TypeScript.

Do not use `any`.

---

# 28. User Identity

Brand DNA must always belong to the authenticated/current user and the selected brand.

Features must use the existing public auth abstraction.

Do not:

- read authentication environment variables directly inside feature components
- hard-code user IDs
- create feature-specific user identity storage
- create fake users
- create feature-local authentication

Brand data must not accidentally cross user or brand boundaries.

---

      └── Brand

            ├── Promise

# 30. Current Stage Definition of Done

Stage 1–2 work is complete only when:

### Brand Promise

- User can see their brand.
- User can provide the core Promise information.
- User can save it.
- User can return later.
- Existing brand functionality remains intact.

### Your Words

- User can provide source material.
- Source material is associated with the correct user and brand.
- User can review their submitted material.
- Original wording is preserved.
- The experience supports the approved capture methods for the implemented slice.

### UX

- The experience feels like telling the system who they are.
- No unnecessary AI terminology is exposed.
- No fake training percentage exists.
- No generic personality score exists.
- Missing information is communicated clearly.
- The user remains in control.

### Engineering

- Strict TypeScript.
- Typed API layer.
- Existing architecture reused.
- Loading states handled.
- Empty states handled.
- Error states handled.
- Retry behavior where appropriate.
- Responsive behavior.
- Accessibility considered.
- Tests added for meaningful behavior.
- No backend files modified without approval.
- No unrelated refactoring.

# 31. Implementation Workflow

For every Brand DNA task:

## Step 1 — Understand

Read:

    docs/BRAND_DNA_PRODUCT_SPEC.md
    docs/BRAND_DNA_IMPLEMENTATION.md

Then inspect the current application.

---

## Step 2 — Architect

Use the Architect agent for meaningful feature work.

Architect must:

- inspect the existing frontend
- inspect relevant backend contracts
- identify reusable components
- identify affected files
- identify API requirements
- identify backend gaps
- produce an implementation plan
- remain read-only

---

## Step 3 — Developer

Developer implements only the approved scope.

Developer must:

- inspect before editing
- make the smallest coherent change
- reuse existing architecture
- avoid unrelated refactors
- run relevant tests
- run type checking
- run lint/build where appropriate
- never commit or push unless explicitly requested

---

## Step 4 — Debug

If something fails:

Use the Debugger agent.

Debugger must:

- reproduce or inspect evidence
- identify the actual cause
- make the smallest fix
- avoid speculative changes
- avoid backend changes unless approved

---

## Step 5 — Review

Use the Code Reviewer agent before considering the slice complete.

Review:

- product alignment
- scope
- API correctness
- type safety
- regressions
- accessibility
- security
- unnecessary complexity
- future-stage contamination

---

# 32. Stop Conditions

Stop and ask for clarification when:

- the product specification is ambiguous
- the backend contract is insufficient
- implementation requires a backend change
- implementation would change existing generation behavior
- implementation requires a new architecture not covered by the current system
- a destructive data migration is required
- authentication behavior must change
- existing functionality would need to be removed
- the requested feature belongs to a later Brand DNA stage

Do not solve uncertainty by inventing behavior.

---

# 33. Stage Boundaries

The following boundaries are intentional.

## Stage 1–2

BUILD:

- Brand Promise
- Your Words
- Interview/paste/type capture appropriate to the approved slice
- source material storage and retrieval
- Brand Home foundation

DO NOT BUILD:

- Voice Study
- automatic voice extraction
- edit learning
- audience learning
- performance learning
- automatic channel optimization
- connected-account ingestion
- advanced publishing
- AI scoring

---

# 34. Future Stage Gate

Before beginning Stage 3, verify:

- Stage 1 provides a useful Brand Promise.
- Stage 2 contains real user material.
- The product can show the user what information has been captured.
- The data model preserves source material correctly.
- The UX has been validated enough to justify deeper personalization.

Do not build Stage 3 simply because the architecture allows it.

---

# 35. Product Quality Test

For future generated content, one of the most important tests is:

> Could a stranger have generated this?

If yes, the Brand DNA system has not captured enough of the user.

Another test:

> Would the user's customer recognize this as something they would say?

The long-term goal is recognizable identity combined with improved communication.

---

# 36. Anti-Rabbit-Hole Rule

When deciding between:

A. building the smallest feature that proves the Brand DNA thesis

and

B. building infrastructure that might be useful later

choose A.

Do not build speculative infrastructure.

Do not create abstractions merely because the future architecture may need them.

Do not turn Brand DNA into a platform before proving that users value the core experience.

---

# 37. Final Product Principle

The product should never feel like:

    "Give our AI enough settings so it can pretend to be you."

It should feel like:

    "Tell us who you are.
     Give us the things only you know.
     We will do the writing work.
     And over time, we will get better at sounding like you."

The user's expertise is the raw material.

Their voice is the identity.

Their corrections are the learning signal.

AI is the writing and improvement layer.

The product wins when the user can say:

> "Yes. That's exactly how I would say it — only better."
